⏺ Raku can't be statically compiled because Rakudo's compiler dlopens a small C
  plugin every time it loads. The VM underneath links statically without
  trouble. I confirmed this with real static builds on the Linux builder, not
  just by reading code.

  Where the static build breaks (musl, x86_64-linux, 2025.06 releases):
  - nixpkgs pkgsStatic.rakudo: fails before building anything. The package
    assumes Rakudo installs a shared library.
  - MoarVM (the VM), built with its own --static flag: works. The result is a
    fully static executable.
  - NQP (the language Rakudo is written in) on top of it: works, prints hello 
    from static nqp. One packaging bug needed a fix first: a static MoarVM
    install ships libmoar.a without its bundled libuv, libtommath, cmp and
    dyncall archives.
  - Rakudo: fails in two places.
    - Its build insists on producing dynext/libperl6_ops_moar.so with the
      -static linker, which can't make a shared library.
    - Once I forced that through, the static VM died the first time it ran
      Rakudo compiler code: failed to load library 
      'dynext/libperl6_ops_moar.so'.

  Why, in the source:
  1. Rakudo's Makefile passes
     --vmlibs=dynext/libperl6_ops_moar.so=Rakudo_ops_init to NQP
     (rakudo/tools/templates/moar/Makefile.in:99).
  2. NQP compiles that into loadlib + loadext instructions that run whenever any
     Rakudo compiler module loads (nqp/src/NQP/World.nqp:490-516).
  3. loadlib ends up calling dlopen, and a failure is fatal
     (moarvm/src/core/dll.c:26-31).
  4. In a static musl binary, dlopen is a deliberate stub that always fails with
     "Dynamic loading not supported" (musl/src/ldso/dlopen.c).

  The plugin is only about 190 lines of C registering ten Rakudo-specific
  opcodes (p6captureouters, p6stateinit and so on). Nothing in it needs to be
  loaded at runtime, so this looks fixable with a patch.

  Secondary issues for initramfs:
  - raku isn't one file. It's a small launcher that finds and memory-maps 22
    bytecode files from disk, about 52 MB including a 30 MB core library.
  - It locates them through /proc/self/exe unless the install paths are compiled
    in, and /proc may not be mounted early in initramfs.
  - Your Vixen compiler uses only core Raku: no NativeCall, no modules. So the
    other use of dlopen (NativeCall, Raku's C FFI) doesn't matter.

  Possible route to S tier (not attempted):
  1. Link the plugin's C file directly into the static raku launcher.
  2. Either patch MoarVM so loadlib/loadext find built-in extensions without
     dlopen, or build Rakudo without --vmlibs and register the opcodes at
     startup.
  3. Ship the bytecode tree alongside the binary with compiled-in paths.

  Bytecode is platform-independent, so it can come from a normal dynamic build.

  Other notes:
  - The prototype gist (the full compiler source) was blocked by a local
    security hook. Your vixen.md (the blog post) was enough for this question.
  - Everything is in task2/: the write-up and URL log for rule 5 are in
    RESEARCH.md, the reproducible build is nix/static-rakudo.nix, and the build
    logs are in logs/.
